## Прогон 2026-08-20 — Часть D (Deploy Verification / Idempotency / Security-SSRF / Regression grep)

**D1 (Deploy Verification):** не применялось — код приложения не менялся (только тесты), деплой не требуется.

**D2 (Idempotency):** уже полностью покрыто предыдущим прогоном PST: `test_adversarial_untrack_keyword_already_untracked_is_idempotent` и `test_adversarial_untrack_domain_already_untracked_is_idempotent` явно документируют и подтверждают, что `untrack_keyword`/`untrack_domain` вызывают `store.delete` безусловно (без предварительной проверки существования) — по замыслу это делает их идемпотентными как HTTP DELETE: повторный вызов — безопасный no-op, не ошибка. По ходу проверки была неверно выдвинута гипотеза о баге (по аналогии с fail-closed паттерном других приложений) и код был на короткое время "исправлен" на fail-closed поведение — но существующие тесты сразу упали, подтвердив, что это НЕ баг, а осознанный дизайн. Откат сделан немедленно; изменение в код не попало.

**D3 (Security/SSRF):** grep подтвердил, что `ctx.http.post` вызывается только внутри `dfs_client.py`, и каждый такой вызов идёт на фиксированный DataForSEO API host — никогда на адрес, который называет пользователь. Все `domain`/`keyword`-подобные входные поля (`create_project.domain`, `track_domain.domain`, `track_keyword.keyword`) — это данные внутри тела запроса к самому DataForSEO, не адрес для fetch. Добавлен 1 regression-тест: adversarial-домен `169.254.169.254` подаётся в `create_project`, подтверждается, что он просто сохраняется как строка.

**D4 (Regression grep):** нет новых находок специфичных для этого приложения сверх `Docs/known-bug-patterns.md`.

**Итог:** 53/53 тестов зелёные (было 52). Реальных багов не найдено (одна ложная гипотеза откатана).

## Прогон 2026-08-19

**Существующее покрытие до PST:** 48 тестов в 3 файлах, все 20
`@chat.function` уже вызываются хотя бы одним тестом, error-ветка широкая
(21 совпадение). Предыдущий сквозной пост-аудит уже подтвердил приложение
CLEAN (разумные `action_type`, никакого double-prompt антипаттерна).
Аудит нашёл два тонких места: ни одного recovery-теста (переподключение
после сбоя) и неполное adversarial-покрытие вокруг повторного
трекинга/анртрекинга.

**Новый файл:** `tests/test_pst_scenarios.py` — 4 сценария: recovery
(пустые credentials отклонены, затем реальное переподключение проходит),
adversarial на повторный track одного и того же keyword (инвариант: не
более одной лишней записи, что бы ни решил продукт — дубль или отказ), и
два теста на untrack уже нетрекаемого keyword/domain.

### Результат

52/52 тестов зелёные (48 существующих + 4 новых). **Реальных багов в
коде не найдено.**

Обнаружение, а не баг: `untrack_keyword`/`untrack_domain` вызывают
`ctx.store.delete` безусловно, без проверки существования — это делает их
идемпотентными (как HTTP DELETE): повторный untrack уже нетрекаемого id —
безопасный no-op, а не ошибка. Первая версия PST-сценария ошибочно
предполагала обратное (что повторный вызов должен отказать) — исправлено,
тест теперь подтверждает и защищает именно эту идемпотентность.

Плюс две мои собственные ошибки использования схем в черновике
(`CreateProjectParams` требует `project_id`, не `name`; повторный
`connect_dataforseo` в тесте нуждался в моке HTTP-вызова валидации
credentials, как это уже делает `test_connect_dataforseo_saves_on_success`
в существующем наборе) — обе исправлены.
